# AGENTS.md

## Источники истины

- `PLAN.md` — зафиксированные решения и порядок реализации MVP. Это спецификация, а не отчёт о текущем состоянии. Перед реализацией любой части MVP прочитай его целиком: форматы API, лимиты, архивация и схема БД описаны только там.
- `CONTEXT.md` — снимок текущего состояния (что уже реализовано). Держи его в пределах 16 КБ и обновляй при изменении состояния; историю решений оставляй в `PLAN.md`.

## Команды

- `make test` или `go test ./...` — unit-тесты. Интеграционные тесты пропускаются без `TEST_DATABASE_URL`.
- `make test-integration` — поднимает PostgreSQL через `compose.yaml` и гоняет всё; тесты создают временную схему.
- `go test ./internal/api -run TestName -v` — один пакет или тест.
- `make vet` / `go vet ./...`, `make fmt` / `gofmt -w .`.
- `make run` — сервер; `make up` / `make down` — PostgreSQL.
- `go run ./cmd/min-msgr-devkey -login alice -label 'My Agent'` — создать пользователя, чат и ключ для ручной проверки.

## Раскладка

- `cmd/min-msgr` — сервер: миграции при старте, HTTP API.
- `cmd/min-msgr-devkey` — dev-утилита, не часть сервера.
- `internal/db/migrations` — встроенные SQL-миграции. Не редактируй уже применённую миграцию; добавляй новый файл.
- `internal/api` — REST, `internal/store/postgres` — SQL, `internal/service` — доменные операции, `internal/markdown` — sanitization.
- `internal/oauth` — провайдеры GitHub/Google/Yandex, `internal/web` — SSR-страницы, OAuth-callback и сессионные cookie.
- `internal/testdb` — изолированная схема для интеграционных тестов.

## Схема БД

- `messages.seq` — глобальный `BIGSERIAL`; уникальность в чате — `UNIQUE (chat_id, seq)`. Не заменяй на `max(seq)+1`.
- Идемпотентность агентских сообщений — частичный уникальный индекс `(chat_id, client_message_id)`.

## Стек

Go; PostgreSQL (любое изменение схемы — только через миграции); серверный рендеринг Go-шаблонами + HTMX; WebSocket для веб-интерфейса; всё в одном бинарнике. Архивы — на локальной ФС, путь в конфиге.

## Жёсткие правила

- Вход — через OAuth (GitHub/Google/Yandex); первый успешный вход = регистрация. Первый админ создаётся через БД, управление админами — консольной утилитой.
- Внутренний ID пользователя — `<oauth_login>#<3 цифры>` (уникален глобально); отображаемое имя — только логин, совпадения допустимы.
- Пользователь общается только со своими агентами; доступа к чужим чатам и агентам нет.
- 1 API-ключ = 1 чат. Метка ключа — имя чата; переименование запрещено.
- Агент не хранится в БД: `agent_name` приходит в каждом сообщении. Отображение — `<agent_name>@<oauth_login>`.
- Ключ `sk_...` показывается один раз; в БД хранится только SHA-256. Ротация перезаписывает хэш in-place, история ключей не хранится.
- Агентский API — только REST `/api/v1/messages`; веб-интерфейс читает и пишет только через WebSocket.
- Тело сообщения — CommonMark. Raw HTML, ссылки, изображения и автолинки запрещены; sanitization обязательна и на сервере, и на клиенте.
- Отзыв ключа: сначала сформировать архив `.md` → `.zip` (хранится 30 дней), затем удалить чат и сообщения из БД.
- Лимиты истории: дни и байты на чат (пользователь — в пределах админских максимумов), общий лимит байт на пользователя (только админ). После любого trimming отправляй `history.trimmed`.
- Админ не имеет доступа к содержимому чатов; своих чатов у него нет.

## Git

Обязателен skill `git-flow` (`.agents/skills/git-flow/SKILL.md`). Критично:

- Любая изменяющая Git-операция (commit, branch, merge, rebase, push, tag, reset…) — только по явному поручению и после отдельного подтверждения непосредственно перед выполнением. Одно подтверждение = одна операция.
- Push и merge в `main`/`master` выполняет разработчик; агент их не выполняет.
- Коммит однострочный: `<type>: #<issue> (spec <spec>) | <описание>`; без задачи — `<type>: #NO-TASK | <описание>`. Без body, footer, `BREAKING CHANGE` и `Co-authored-by`.
- Ветки: `specs/<номер-спецификации>-<english-description>` и `release_<номер-релиза>`.
