# Skill: git-worktree-issue
# Хук before_implement: worktree по issue

Создаёт git worktree с веткой спеки для issue, по которому запущен
`/speckit-implement`, — вся реализация дальше идёт только в нём (git-flow:
работа в worktree и spec-ветке).

## Вход

Аргумент вызова (`$ARGUMENTS`) — то, что пользователь передал `/speckit-implement`
(например, `issue 0050`). Если аргумент пуст, issue и спека берутся из текущей
спецификации: `.specify/feature.json` → `feature_directory` → в `spec.md` строка
`**Input**: … "issue NNNN"`.

## Шаги

1. **Определить issue**: номер из аргумента (`0050`, `50`, `issue 0050`) или из
   Input спеки. Не нашёлся — остановиться и спросить владельца.
2. **Определить spec-id** — имя каталога спецификации:
   - по возможности codedocs (таблица Issues, documentId 3488): колонка `spec-id`
     записи с номером issue (`datatable_get_rows`, фильтр `eq` числом);
   - иначе — `feature_directory` из `.specify/feature.json` без `specs/`.
3. **Имена**:
   - ветка — `specs/<spec-id>` (например, `specs/021-attachment-preview`);
   - каталог worktree — `../<имя-репозитория>-issue-<NNNN>` (например,
     `../organizer-mvp-issue-0050`); база ветки — `develop`.
4. **Проверить состояние** (чтение, без подтверждений):
   - если worktree с такой веткой уже есть (`git worktree list`) — использовать
     его, шаги 5–6 пропустить;
   - главный чекаут: ветка `develop`, совпадение с `origin/develop` (если
     расходится — показать и спросить);
   - неотслеживаемая копия `specs/<spec-id>/` в главном чекауте — это артефакты
     спецификации (specify/plan/tasks ещё не закоммичены): запомнить для шага 6.
5. **Создать worktree** — одна git-операция, по отдельному подтверждению
   владельца (git-flow), с показом точной команды:
   ```bash
   git worktree add -b specs/<spec-id> ../<имя-репозитория>-issue-<NNNN> develop
   ```
   Если ветка уже существует локально — `git worktree add ../<…> specs/<spec-id>`
   (без `-b`). Других git-операций хук не делает: коммиты — задачи реализации,
   push — только владелец.
6. **Перенести артефакты спецификации**, если их нет в worktree (созданы в
   главном чекауте и не закоммичены): `specs/<spec-id>/` из главного чекаута в
   worktree. Коммитит их задача T001.
7. **Подготовить окружение worktree**: `make setup` (npm-зависимости обоих
   фронтендов) — без него `make lint` падает на `build-frontend`. Долгая
   команда — сообщить, что идёт установка.
8. **Отчёт** — обязательно текстом и JSON-строкой, чтобы `/speckit-implement`
   продолжил в worktree:

   ```text
   WORKTREE: <абсолютный путь>
   BRANCH: specs/<spec-id>
   ISSUE: <NNNN>
   ```

   ```json
   {"WORKTREE_PATH": "<абсолютный путь>", "BRANCH_NAME": "specs/<spec-id>", "ISSUE": "<NNNN>", "SPEC_ID": "<spec-id>"}
   ```

9. **Дальше — только в worktree**: все правки кода, тесты, `make fmt/lint/test`
   и коммиты (`<тип>: #<issue> (spec <spec-id>-T<NN> | …)`) выполняются в
   каталоге worktree; пути задач вида `core/…`, `mail/…` разрешаются от его
   корня. Главный чекаут до слияния не трогается (кроме шага 5).

## Правила

- git-flow: изменяющая git-операция здесь ровно одна (шаг 5) и только после
  отдельного подтверждения; ветки спеки хук не удаляет; push не выполняет.
- Если ветка спеки уже слита в develop (работа завершена) — сказать об этом и
  остановиться, worktree не создавать.
- Спорные состояния (расхождение с origin, грязный индекс в главном чекауте) —
  показать владельцу и спросить, молча не продолжать.
