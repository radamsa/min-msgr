# Git Flow для проекта

## Назначение

Этот skill определяет правила работы агента с Git-репозиторием проекта.

Агент обязан соблюдать эти правила при анализе Git-состояния, подготовке изменений, работе с ветками и коммитами.

## Общие правила

Для управления версиями проекта используется Git.

Основные типы веток:

* `specs/*` — разработка конкретной задачи в рамках спецификации (при использовании SpecKit);
* `release_*` — подготовка конкретного релиза и исправление замечаний внутренней приемки;
* `master` / `main` — основная ветка с принятыми изменениями.

При использовании SpecKit для каждой задачи создается отдельная `spec`-ветка.

Любое изменение исполняемого кода или SQL **ДОЛЖНО** быть связано с задачей в трекере.

Изменения файлов, не влияющих на логику исполнения приложения, могут выполняться без задачи.

## Полномочия агента

Разработчик управляет состоянием Git-репозитория.

Агент:

* **МОЖЕТ** читать состояние репозитория;
* **МОЖЕТ** анализировать ветки, коммиты и diff;
* **МОЖЕТ** предоставлять рекомендации;
* **НЕ МОЖЕТ** самостоятельно изменять состояние Git.

Любая Git-операция, изменяющая состояние репозитория, может быть выполнена агентом только по явному поручению разработчика и после отдельного подтверждения непосредственно перед выполнением.

Разрешение на одну операцию **НЕ распространяется** на последующие операции.

Слияние в `master` / `main` **ВСЕГДА** выполняет разработчик.

К изменяющим Git-операциям относятся, в частности:

* создание или удаление веток;
* commit;
* merge;
* rebase;
* cherry-pick;
* reset с изменением состояния;
* tag;
* push;
* и другие операции, изменяющие Git-состояние.

## Ветки

### Spec-ветки

При использовании SpecKit имя `spec`-ветки должно соответствовать формату:

```text
specs/<номер-спецификации>-<краткое-описание-на-английском>
```

Требования:

* номер спецификации;
* краткое описание на английском языке;
* отдельные слова в описании разделяются дефисами.

Допустимые примеры:

```text
specs/495-interface-settings
specs/020-slow-query-fix
```

Недопустимые примеры:

```text
495
task-20
bug-fix
spec/495-interface-settings
spec/495-123-настройки
```

`specs`-ветка одновременно является task-веткой.

После завершения разработки изменения из `specs`-ветки включаются в соответствующую `release`-ветку.

Удаление `specs`-ветки после завершения работы выполняет пользователь вручную.

Агенту запрещено самостоятельно удалять `specs`-ветки.

### Release-ветки

Имя release-ветки должно соответствовать формату:

```text
release_<номер-релиза>
```

Примеры:

```text
release_0.1.10
release_1.2.0
```

Release-ветка используется для подготовки соответствующего релиза и исправления замечаний внутренней приемки.

### Запись ветки в codedocs (колонка «Git branch» таблицы Issues)

В колонке записывается **только имя ветки, в которой велась основная разработка** — обычно `specs/<…>`, при работе прямо в develop — `develop`.

Без дополнительного текста: никаких пояснений в скобках, номеров коммитов, слов о слиянии и отправке.

Допустимо: `specs/021-attachment-preview`, `develop`.

Недопустимо: `develop (слита specs/021…; merge b23f256)`, `specs/021-… (не отправлены)`.

Указание владельца от 2026-11-05.

### Master / Main

`master` / `main` содержит принятые изменения.

Агент **НИКОГДА** не выполняет merge, rebase, push или другие изменяющие операции непосредственно в `master` / `main`.

Слияние изменений в `master` / `main` выполняет только разработчик.

## Сообщения коммитов

Используется упрощенный формат Conventional Commits.

Для изменений, связанных с задачей в трекере, формат:

```text
<type>[!]: #<номер issue> (spec <номер-спецификации>-<номер-задачи>) | <краткое описание>
```

Примеры:

```text
feat: #0036 (spec 001-T023) | добавили экспорт отчета
fix: #0001 (spec 997-T495) | исправили таймаут запроса
docs: #9999 (spec 120-T130) | уточнили инструкцию запуска
```

Для изменений, которые по правилам проекта могут выполняться без задачи, используется формат:

```text
<type>[!]: #NO-TASK | <краткое описание>
```

Пример:

```text
docs: #NO-TASK | уточнили инструкцию запуска
```

Допустимые типы:

| Тип        | Назначение                          |
| ---------- | ----------------------------------- |
| `feat`     | новый функционал                    |
| `fix`      | исправление ошибки                  |
| `chore`    | технические изменения               |
| `build`    | система сборки и зависимости        |
| `ci`       | CI и связанные скрипты              |
| `docs`     | документация                        |
| `perf`     | повышение производительности        |
| `refactor` | рефакторинг без изменения поведения |
| `style`    | форматирование и стиль кода         |
| `test`     | тесты                               |
| `revert`   | отмена предыдущего изменения        |

Дополнительные структурные элементы сообщения коммита **НЕ предусматриваются**.

Не использовать:

* `body`;
* `footer`;
* `BREAKING CHANGE`;
* `Co-authored-by`;
* другие дополнительные секции.

Сообщение коммита должно быть **однострочным**.

## Алгоритм поведения агента

### Когда агент анализирует репозиторий

Агент может выполнять только операции чтения, например:

* проверять текущую ветку;
* проверять статус рабочего дерева;
* просматривать существующие ветки;
* анализировать историю коммитов;
* анализировать diff;
* проверять наличие и имена release/spec-веток.

Операции чтения не требуют подтверждения разработчика.

### Когда требуется изменить Git-состояние

Перед выполнением каждой отдельной изменяющей Git-операции агент обязан:

1. определить конкретную операцию;
2. сообщить разработчику, что именно будет изменено;
3. указать соответствующую команду или эквивалентную Git-операцию;
4. запросить отдельное подтверждение;
5. после подтверждения выполнить **только эту одну операцию**;
6. после выполнения считать подтверждение исчерпанным.

Общее согласие вроде:

```text
сделай всё
```

не считается разрешением на несколько последовательных изменяющих Git-операций.

Каждая последующая изменяющая операция требует нового подтверждения.

Явное поручение конкретной операции, данное непосредственно перед ее выполнением, считается запросом на выполнение этой операции, но агент все равно обязан получить подтверждение непосредственно перед выполнением.

### Перед созданием коммита

Агент обязан проверить:

1. если изменен исполняемый код или SQL — изменение связано с задачей в трекере;
2. если используется задача — номер задачи известен;
3. если изменение выполняется в рамках спецификации — номер спецификации известен;
4. сообщение соответствует установленному формату;
5. сообщение однострочное;
6. отсутствуют `body`, `footer`, `BREAKING CHANGE`, `Co-authored-by` и другие дополнительные секции.

Перед выполнением `git commit` требуется отдельное подтверждение разработчика.

### Перед созданием spec-ветки

Если используется SpecKit, агент обязан проверить соответствие имени:

```text
specs/<номер-спецификации>-<номер-задачи>-<english-description>
```

Создание ветки является отдельной изменяющей Git-операцией и требует отдельного подтверждения.

### Перед созданием release-ветки

Агент обязан проверить соответствие имени:

```text
release_<номер-релиза>
```

Создание release-ветки является отдельной изменяющей Git-операцией и требует отдельного подтверждения.

### Перед включением spec-ветки в release-ветку

Агент может подготовить команду и сообщить необходимые действия.

Самостоятельно выполнять merge или rebase агент не должен без отдельного подтверждения.

Включение изменений в `master` / `main` агент не выполняет ни при каких обстоятельствах.

### Перед удалением spec-ветки

Удаление `spec`-ветки выполняется пользователем вручную.

Агенту запрещено самостоятельно удалять `spec`-ветки.

## Критические запреты

Агент **НЕ ДОЛЖЕН**:

* самостоятельно выполнять Git-операции, изменяющие состояние репозитория;
* выполнять несколько изменяющих Git-операций по одному подтверждению;
* выполнять commit без отдельного подтверждения;
* самостоятельно выполнять merge в `master` / `main`;
* самостоятельно выполнять push;
* самостоятельно удалять `spec`-ветки;
* создавать release-ветку с именем, не соответствующим формату;
* создавать spec-ветку с именем, не соответствующим формату;
* создавать коммиты с многострочным сообщением;
* добавлять `body`, `footer`, `BREAKING CHANGE`, `Co-authored-by` или другие дополнительные секции в commit message;
* менять исполняемый код или SQL без привязки к задаче в трекере;
* использовать формат commit message, отличный от установленного в этом skill.
