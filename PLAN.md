# План: минималистичный Markdown-чат «пользователь ↔ AI-агенты»

Ниже — зафиксированные решения и план реализации. Всё, что мы обсудили, сведено в единый документ.

---

## 1. Концепция и правила

- **Чат** — обмен сообщениями между пользователем и его агентами. Жёсткое правило: **1 API-ключ = 1 чат**.
- **Пользователь** общается только со своими агентами. Между пользователями и чужими агентами связи нет.
- **Агент** — не сущность в БД. Его имя передаётся в каждом сообщении и хранится только в сообщении.
- **Отображение:** пользователь — `<oauth_login>`, агент — `<agent_name>@<oauth_login>`. Имена пользователей могут совпадать (различаются внутренним `#NNN`), это нормально.
- **Формат сообщений:** только CommonMark-текст. Запрещены raw HTML, ссылки, изображения, автолинки. Разрешены: `**жирный**`, `*курсив*`, инлайн-код, код-блоки, списки, цитаты, заголовки, горизонтальные линии.
- **История** хранится на сервере, лимитируется по дням хранения и байтам.

---

## 2. Аутентификация и пользователи

- **OAuth-провайдеры:** GitHub, Google, Yandex. Архитектура — с возможностью добавления новых OIDC/OAuth-провайдеров.
- **Первый успешный вход = регистрация.** Отдельного шага подтверждения профиля нет.
- **Внутренний ID:** `<oauth_login>#<3 случайные цифры>`, уникален глобально.
- **Отображаемое имя:** только `<oauth_login>` (без суффикса).
- **Профиль:** email, аватар, отображаемое имя — не обязательны для MVP (уточняется при реализации; по умолчанию можно хранить email из OAuth).

---

## 3. API-ключи и чаты

- Пользователь на странице ключей нажимает **«Создать ключ»**, вводит **метку** → сервер атомарно создаёт **API-ключ + чат**. Метка ключа = название чата.
- **Переименование невозможно.**
- **Формат ключа:** `sk_<base62-случайная-строка>` (префикс для узнаваемости в логах). Хранится **только SHA-256**. Показывается пользователю **один раз** при создании/ротации.
- **Аутентификация агента:** `Authorization: Bearer sk_...` → сервер считает SHA-256, ищет активный ключ, получает `chat_id` и владельца.
- **Ротация:** пользователь может перевыпустить ключ в чате. Старый перестаёт действовать сразу, новый хэш записывается in-place. Чат и история сохраняются. **История ключей не хранится.**
- **Отзыв:** удаление ключа + архивация чата (см. §7).
- **Лимит ключей:** по умолчанию 2, настраивается **админом** (глобально и/или per-user). Пользователю недоступно.

## 4. API для агентов (REST/JSON)

Только для агентов. Пользователь в API не ходит.

**Endpoints:**

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/api/v1/messages` | Отправить сообщение |
| `GET` | `/api/v1/messages?limit=N&cursor=...` | Последние N сообщений (постранично назад) |
| `GET` | `/api/v1/messages?since=<RFC3339>&cursor=...` | Сообщения с даты/времени (постранично вперёд) |

**Отправка сообщения:**

```json
POST /api/v1/messages
Authorization: Bearer sk_...
{
  "agent_name": "MyAgent",
  "body": "**текст** в Markdown",
  "client_message_id": "uuid"   // опционально, для идемпотентности
}
```

Валидация `agent_name`: `[a-zA-Z0-9_-]`, до 16 символов, без `@`, не пустое, регистронезависимая проверка символов; **сохраняется как есть**.

Валидация `body`: trim пробелов по краям; если пусто — `400`. Максимальная длина — глобальный конфиг.

**Ответ истории (оба режима):**

```json
{
  "messages": [ { "seq": 1, "author": "MyAgent@ivan", "body": "...", "created_at": "..." } ],
  "next_cursor": "<opaque|null>",
  "limit": 100
}
```

- Сортировка в ответе — по `seq` возрастанию.
- `limit` клампится до конфиг-максимума; фактическое значение возвращается.
- Курсор opaque (например, base64 от `seq` + направление), клиент его не парсит.
- Курсор и `since` вместе: курсор — позиция, `since` — нижняя граница.
- Если `seq` из курсора уже удалён лимитами — начинаем с ближайшего большего.

## 5. WebSocket (только веб-интерфейс)

Всё чтение и запись пользователя — через WebSocket. JSON-события `{type, payload}`.

**Клиент → сервер:**
- `messages.subscribe` с `since` (при первом подключении — `now - 1h`; при переподключении — время последнего полученного сообщения).
- `messages.before` с `cursor` — листание назад.
- `message.send` с `body` и `client_message_id`.

**Сервер → клиент:**
- `message.created` — новое сообщение (с `seq`).
- `message.ack` / `message.error` — ответ на отправку.
- `messages.page` — страница истории (на subscribe/before).
- `chat.deleted` — при отзыве ключа.
- `history.trimmed` — при удалении старых сообщений лимитами.

**Первичная загрузка:** если за последний час сообщений нет — сервер сразу подгружает последнюю страницу истории, чтобы чат не выглядел пустым. В ответе — `next_cursor` для листания в прошлое.

**Переподключение:** клиент шлёт `since = <время последнего полученного сообщения>`, сервер доотдаёт всё новее.

---

## 6. Лимиты истории

- **Дни хранения** — на чат (настраивается пользователем в пределах админского максимума).
- **Байты на чат** — на чат (настраивается пользователем в пределах админского максимума).
- **Общий лимит байт по всем чатам пользователя** — админская настройка (глобально и/или per-user), пользователю недоступна.
- **При превышении лимита в чате** — удаляются самые старые сообщения этого чата.
- **При превышении общего лимита пользователя** — автоматически удаляются самые старые сообщения **глобально по времени** по всем чатам пользователя.
- **По дням хранения** — плановая задача (крон) удаляет сообщения старше N дней.
- После любого удаления по лимитам в WebSocket уходит `history.trimmed`.

---

## 7. Отзыв ключа и архивация

- **Отзыв** = удаление ключа. Чат **сразу пропадает** из списка чатов, писать и читать его нельзя, API возвращает ошибку.
- В момент отзыва **один раз** формируется архив:
  - `.md`-файл: заголовок с метаданными чата + сообщения вида `## <timestamp> <author>` + тело в Markdown.
  - Упаковывается в `.zip`. Имя: `<label>_<chat_id>_<дата_отзыва>.zip`.
  - Хранится в локальной файловой системе; путь — в конфиге сервиса.
- После формирования архива **записи чата в БД удаляются**.
- Пользователь может **скачивать архив** со страницы управления ключами в течение **30 дней** (рядом — отсчёт до удаления).
- Через 30 дней архив удаляется **безвозвратно** фоновой задачей (крон в приложении).
- Просмотр истории после отзыва **нигде недоступен** — только скачивание архива.

## 8. Веб-интерфейс (SSR Go-шаблоны + HTMX, минимум JS, один бинарник)

| Экран | Содержимое |
|---|---|
| **Логин** | Кнопки GitHub / Google / Yandex |
| **Список чатов** | По одному на ключ: метка, имя агента последнего сообщения, время |
| **Чат** | История (Markdown-рендер), textarea, WebSocket-обновления, листание назад курсором |
| **Управление ключами** | Создание (метка → ключ + чат, ключ показывается один раз), ротация, отзыв, скачивание архива после отзыва, счётчик лимита ключей |
| **Настройки чата** | Лимит дней хранения, лимит байт (в пределах админских максимумов) |
| **Настройки пользователя** | Общий лимит байт (только просмотр, если админский), лимит ключей (только просмотр) |

---

## 9. Админ-панель

- **Роль `admin`.** Первый админ создаётся через БД. Консольная утилита управления админами (назначить/снять).
- **Объём:**
  1. Глобальные дефолты: лимит ключей на пользователя, макс. дней хранения, макс. байт на чат, макс. общий байт на пользователя.
  2. Переопределения на пользователя: те же параметры точечно.
  3. Список пользователей: просмотр, блокировка/разблокировка, удаление.
- **Админ не видит содержимого чатов.** Своих чатов у него нет.
- Аудит доступа админа к переписке не нужен (доступа нет).

## 10. Технологии и инфраструктура

- **Backend:** Go.
- **Frontend:** серверный рендеринг на Go-шаблонах + HTMX, минимум JS, всё в одном бинарнике.
- **БД:** PostgreSQL. Миграции — обязательны.
- **WebSocket:** JSON-события `{type, payload}`.
- **Архивы:** локальная ФС, путь в конфиге.
- **Крон-задачи:** удаление по дням хранения, удаление архивов старше 30 дней.
- **Конфиг сервиса:** OAuth-провайдеры, макс. длина сообщения, макс. кол-во сообщений в выдаче API, путь к архивам, глобальные дефолты лимитов.
- **Безопасность:** ключи — только SHA-256, показ один раз; sanitization Markdown на сервере и клиенте (запрет raw HTML, ссылок, изображений); CORS/rate limits — по необходимости.

## 11. Предлагаемый порядок реализации (MVP)

1. **Схема БД + миграции:** users, oauth_accounts, api_keys (chat_id, label, hash, created_at), chats (id, user_id, label, days_limit, bytes_limit, created_at), messages (id, chat_id, seq, author_type, agent_name, body, bytes, created_at), admin_settings, user_overrides, archives.
2. **OAuth-вход** (GitHub/Google/Yandex) + регистрация + сессия.
3. **Создание ключа + чата**, показ ключа один раз, ротация, отзыв + архивация.
4. **REST API для агентов** (отправка, последние N, since, пагинация, валидация).
5. **WebSocket**: подписка, отправка, ack/error, страницы истории, события.
6. **Markdown-рендер и sanitization** (сервер + клиент).
7. **Лимиты истории**: per-chat, общий, крон по дням, `history.trimmed`.
8. **Веб-интерфейс**: список чатов, чат, управление ключами, настройки.
9. **Админ-панель + консольная утилита админов.**
10. **Архивация и крон удаления архивов.**
11. **Тесты** (unit/integration/e2e), CI, Docker Compose.
